# Use Case Requirements

## Purpose

The monitoring workspace manages independently developed MCP server and web backend repositories. It is the place to register services, clone and update their `main` branches, prepare isolated environments, launch services, inspect availability, and maintain local MCP routing configuration.

The intended audience is the **workspace maintainer** (also called the MCP platform operator), who is responsible for operations and integration. **Service maintainers** own feature development in their respective repositories. A contributor may act as either role or both; the distinction describes responsibilities, not necessarily different people.

## Roles and Actors

### Core Human Roles

- **Workspace maintainer:** edits the workspace registry, synchronizes server repositories, provisions their isolated environments, starts services, checks availability, and maintains workspace-level routing/configuration.
- **Service maintainer:** owns one service repository's code, dependencies, tests, releases, and `main` branch, and keeps its startup behavior compatible with the workspace contract. They do not need to own the monitoring workspace.

### External and Optional Actors

- **MCP host/client:** consumes the tools exposed by a running server through its MCP endpoint.
- **Git hosting provider:** stores each server repository and provides the `main` branch fetched by the workspace.
- **Infrastructure operator (optional):** owns nginx, TLS, firewall, or hosting configuration when those responsibilities are separate from the workspace maintainer. Nginx configuration is not generated by the workspace manager.

## Use Cases

### UC-01: Register an MCP or web service

The workspace maintainer adds a unique name, service type, HTTPS or SSH Git URL, and unused TCP port to `repositories.toml`. MCP repositories expose `mcp-server` and serve Streamable HTTP at `/mcp`. Web repositories provide an argv command, optionally with `{host}` and `{port}` placeholders and an HTTP health path.

**Outcome:** the registry can drive a clone, an isolated environment, a local run command, and a generated VS Code MCP endpoint.

### UC-02: Synchronize registered repositories

The workspace maintainer runs `mcp-workspace sync`. Missing repositories are cloned from `main`. Existing checkouts are fast-forwarded from `origin/main` only when the checkout is clean, on `main`, and has the registered origin URL. Repository content and branch changes remain the service maintainer's responsibility.

**Outcome:** local checkouts reflect the latest fast-forwardable `main` state. Unsafe or ambiguous checkout states stop with an error and are left unchanged.

### UC-03: Prepare server environments

The workspace maintainer runs `mcp-workspace setup`. The workspace synchronizes repositories, creates a `.venv` in each service checkout if absent, and installs that checkout in editable mode using its own `pyproject.toml`. Each service maintainer owns that project metadata and dependency set.

**Outcome:** each server's Python dependencies remain isolated from the workspace manager and from other servers.

### UC-04: Start and monitor a server

The workspace maintainer runs `mcp-workspace run <name>` in a terminal. The manager starts the MCP executable or configured web command in the foreground with localhost binding and its registered port. `mcp-workspace status` reports checkout state and TCP availability; web services may additionally configure an HTTP health path. The MCP host/client connects to MCP endpoints; web clients or the optional infrastructure operator use web backends as appropriate.

**Outcome:** the maintainer can start one server and see basic checkout and endpoint availability. The status check is not an MCP handshake, application health check, or process supervisor.

The workspace maintainer may instead run `mcp-workspace run-all` to launch all registered, provisioned services as foreground child processes. Ctrl+C or an unexpected child exit stops the group; this is a convenience command, not a persistent process supervisor.

### UC-05: Configure local MCP clients

After synchronization or setup, the manager generates `.vscode/mcp.json` from MCP services in the registry.

**Outcome:** VS Code has one local Streamable HTTP endpoint per registered MCP service. Web backends are excluded. Manual changes to this generated file are overwritten by the next `sync` or `setup`.

### UC-06: Add or remove a server from monitoring

The maintainer adds or removes its registry entry. Removing an entry stops it from appearing in generated MCP configuration or management commands; it does not delete the checkout, its `.venv`, or remote data.

**Outcome:** repository cleanup remains a deliberate, separate operation.

## Out of Scope

- Developing server-specific tools, resources, prompts, or business logic.
- Automatically merging local work or resetting a checkout to match remote `main`.
- Automatically deleting repositories, virtual environments, or user data.
- Starting all services as background daemons, restarting failed processes, or managing production deployments.
- Generating nginx configuration, TLS certificates, secrets, or public-facing access policy.
- Claiming client device GPS location; location behavior belongs to a server implementation.
